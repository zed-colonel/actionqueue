# ActionQueue 0.3.0 release preparation and upgrade

Release identity: **0.3.0 / v0.3.0**. Contract: `AQ-CONT-1`, revision
`STACK-2026-07-20-CLEAN-1`. Conformance package: **16**, with immutable fixture and
asset hashes. Rust: **1.89.0**. Store manifest schema **1**, WAL format **1**,
snapshot schema **10**, logical projection and canonical digest version **9**.

This release reduces mutation and restart costs under retained history. It changes
no normative contract, execution semantics, authorization or feature-profile rules.
The developmental profile `STACK-DEVELOPMENTAL-DIAGNOSTICS-1` and its eighteen-case
matrix remain unchanged. Its SHA-256 is
`4bd682ab29d64394e64f56cd0c5f2b944eddfc137fcd5b6e3e035b50218617c6`.

## Changes and Rust API compatibility

- Structurally shared projections copy changed paths and records during mutation.
  Dependency, hierarchy, subscription and active-run coordination update incrementally.
- Daemon publication shares immutable roots, including an equal-revision fast path.
  Checkpoint capture flushes the WAL and records matching immutable roots/cursor
  under authority ownership; encoding and publication run outside the mutation lane.
- Schema-10 checkpoints bind store identity, manifest, covered WAL offsets and
  boundary hashes. Proven checkpoint publication performs zero WAL reads and zero
  reducer applications. Compact binary sections preserve logical projection v9.
- History getters that previously returned slices now return `History<T>`. Iterate
  over the history or call `to_vec()` when an owned copy is required. Review Rust
  integrations for slice assumptions before updating their dependency.

[ADR-019](../adrs/AQ-ADR-019-structurally-shared-projections.md) and
[ADR-020](../adrs/AQ-ADR-020-bounded-snapshot-bootstrap.md) describe the architecture.

## Recovery integrity and store upgrade

Ordinary writable startup hydrates a validated snapshot, checks sequence 1's
manifest binding and the last covered frame's sequence, hash and exact offsets,
then seeks directly to and replays the WAL tail. Snapshot reading, validation,
hydration and index construction still scale with snapshot size. The complete WAL
remains mandatory, even when a checkpoint is available.

**Ordinary startup does not rehash the skipped WAL prefix.** Changes wholly within
that prefix can go undetected when the checked boundary remains identical.
Checkpoint commitments establish integrity, not publisher authentication. A missing
or physically damaged snapshot permits WAL-only recovery. Identity, compatibility,
semantic and boundary failures halt startup; they do not trigger that fallback.
Explicit full verification rejects a present damaged snapshot.

Stop the source owner before these offline commands; a live writer causes
`StoreInUse`. To upgrade a released schema-9 AQ-CONT-1 store:

```sh
actionqueue store upgrade --data-dir SOURCE --output DEST
actionqueue store verify --data-dir DEST --json
```

Upgrade preserves the source and creates a separate destination through staging.
It fully verifies both stores, preserves UUID, creation fields, feature profile,
domain history and logical projection digest, and changes the destination snapshot
schema to 10. Sequence 1 is regenerated to bind the new manifest; subsequent WAL
frames remain byte-for-byte identical. Populated or overlapping destinations fail.
Keep the source until the destination and the application have been checked, then
configure the owner to use DEST.

Writable opening does not silently migrate schema 9. Pre-contract stores and
older unreleased development schemas remain unsupported. Downgrade and automatic
restore-time migration remain unsupported: upgrade the source/backup first, then
create a schema-10 backup with a fresh descriptor. Feature profiles are immutable;
a broader binary does not upgrade a store's capabilities.

`actionqueue store verify --data-dir DIR --json` is read-only and validates the
complete retained WAL, recomputes the covered commitment, compares checkpoint and
replayed projection digests and operation associations, and verifies tail parity.
It does not initialize, repair, reconcile execution or run handlers. Backup/restore
and upgrade also validate complete history. Backup may omit a physically damaged
source snapshot after fully validating its WAL; included and staged snapshots are
fully verified. External artifact bytes remain application-owned.

This store command is separate from `python3 -B scripts/release.py verify`, which
checks release artifacts and gate evidence against an exact clean source commit.
See the [operator recovery guide](../wal-recovery-guide.md).

## Measured budgets

These are fixed storage-boundary workloads on a shared workstation, with warm OS
caches and no forced eviction or CPU isolation. They exclude handler execution,
fixture construction, and daemon publication from mutation timings. They are not
general throughput guarantees or WorldInterface end-to-end certification.

The [instrumented 0.2.0 baseline](../performance/retained-history-0.2.0.md), measured
2026-10-17 at `7986dde92a43306fed384c9e6ef41c3991b36384`, used the released 0.2.0
algorithms and one sample per size. Each operation cloned the complete projection.
Admissions grew from **2.825 ms** at 1,000 terminal runs to **26.199 ms** at 10,000;
cancellations grew from **2.989 ms** to **25.430 ms**. The quadratic baseline was
not run at 100,000.

Fresh AQ-P5 measurements on **2026-10-21 UTC** used five repetitions per size,
Rust/Cargo 1.89.0, x86-64 Linux 7.2.8-9, an Intel Core i9-9900K and ext4/NVMe.
Runtime code was `29de2bba876bf35bc3f221f4e06170f7903f2807` with this release's
version/documentation/tooling edits; no runtime algorithms changed in AQ-P5.
Values below are medians of the five batch means, in milliseconds per operation.

| Retained terminal runs | Admission median (ms/op) | Cancellation median (ms/op) |
|---:|---:|---:|
| 1,000 | 0.734456 | 0.736769 |
| 10,000 | 1.641040 | 1.430103 |
| 100,000 | 0.840074 | 0.814070 |

The 100,000/1,000 growth ratios are **1.143804×** for admission and
**1.104918×** for cancellation, both within the **≤2×** budget.
The 10,000-run admission sample set was slower than either endpoint; all samples
are retained rather than interpreted as a monotonic throughput curve.
Raw reports and logs are in run `3f0eff5c-1780-4801-a8d6-15bc0e45c19e`,
`scratch/verification/aq-p5-retained-history.json` and `.log`, with environment
in `measurement-environment.txt` and computed medians in `aq-p5-mutation-summary.json`.
Reproduce from the repository root with the supplied `TMPDIR` and `CARGO_TARGET_DIR`:

```sh
cargo bench --locked --bench retained_history -- --retained-runs 1000 --retained-runs 10000 --retained-runs 100000 --repetitions 5
```

The [AQ-P2 protocol](../performance/retained-history-aq-p2.md) defines independent
copied prefixes and fresh writer sessions for each repetition. Each sample admits
100 fresh tasks and cancels those 100 runs with immediate durability, at 1,000,
10,000 and 100,000 retained canceled Once runs, fixed three-byte payloads, unique
admission keys, single-tenant scope and no optional store features. Full recovery,
WAL-byte and canonical-digest checks run outside mutation timers. Structural
assertions remain enabled: at most **10 record materializations per admission**,
**20 per cancellation**, and exactly **two shallow projection clones per operation**.

Historical [AQ-P3 measurements](../performance/aq-p3-bootstrap.md), from 2026-10-20,
used three alternating paired startup samples per size against identical WAL bytes,
with a 200-event tail. Median snapshot/WAL-only startup ratios were **0.124309** at
10,000 retained runs and **0.065386** at 100,000, both below the **0.5** budget.
The same benchmark read exactly **202 frames** and applied **200 reducer events**
for that tail, including both boundary probes. Aggregate hydration grew
**7.579809×** against **10.132306×** serialized-byte growth. The large complete
checkpoint was **40,434,242 bytes**, below the unchanged **256 MiB (268,435,456-byte)**
ceiling, versus **262,703,635 bytes** for schema 9. Snapshot hydration is not constant
in retained size; tail replay is bounded by tail length.

## Retention and certification scope

Terminal archival is an accepted design only in
[ADR-021](../adrs/AQ-ADR-021-retained-terminal-history.md); it does not ship here.
Complete WAL and terminal history remain retained, and compaction is absent.
Snapshot and row ceilings can still prevent checkpoint publication as history grows.
Inspection remains bounded, paginated and redacted; references grant no authority.

Certification covers the ActionQueue-owned reference adapter and
[independent outbox consumer](../examples/downstream-handoff.md). No actual
WorldInterface or Exoskeleton revision is certified. WorldInterface updates its
pin and certifies its adapter in its own work item. The unpublished acceptance
harness and example retain their independent versions. No unrelated dependencies
are upgraded.

## Prepare an exact candidate

CraftingTable integrates approved work into `aq-perf-1` under the recorded operator
policy. The operator owns final cutover, tagging and publication. This work item
performs none of those operations. Select the eventual release SHA first; a merge
that changes the commit requires fresh evidence even if its tree matches.

On a clean checkout with Rust 1.89.0 and Python 3.11+:

```sh
python3 -B scripts/release.py prepare --version 0.3.0 --commit "$(git rev-parse HEAD)" --output "$TMPDIR/aq-release-0.3.0"
python3 -B scripts/release.py verify --manifest "$TMPDIR/aq-release-0.3.0/release-manifest.json"
```

The output directory must be empty and outside the checkout. **Prepare runs the
expensive gates and invokes verify internally.** Standalone release verification
validates existing evidence and artifacts; it does not rerun the matrix. Preparation
records source identity before and after every gate and never imports arbitrary
older reports. Dirty source, missing/failed gates, incomplete full/developmental
proof, inconsistent versions/hashes, unresolved `docs/releases/blockers.json`
entries and missing artifacts reject release. Preserve failed logs and choose a
new output directory when retrying.

The unchanged gates cover all **eight** feature combinations, workspace tests,
format/clippy/build, production CLI/daemon builds, serde tests, conformance and
developmental aliases, the full report, cross-feature persistence, continuation
benchmarks, rustdoc/link checks, the independent consumer and Cargo packages.
Timing budgets above use the attributed retained-history evidence; they are outside
ordinary CI. Production consumer graphs reject test instrumentation.

Package validation produces actual `.crate` archives. A temporary directory source
seeds all candidate versions together to resolve mutual development dependencies,
then replaces seeds with generated archives and builds registry-only consumers
without root patches. This validates package contents and resolution before
crates.io contains 0.3.0; it does not establish registry availability.

## Publication checklist (operator)

1. Confirm recorded approval policy permits cutover. Integrate/cut over, select the final SHA, and run preparation on that exact clean commit.
2. Verify `release-manifest.json` and `SHA256SUMS`. Review limitations and the evidence logs. The versioned [schema](release-manifest.schema.json) describes the artifact; the verifier additionally checks semantic completeness against the checkout.
3. Create `v0.3.0` at the manifest SHA. Publish the eleven validated crates to crates.io in dependency order: core, storage, executor-local, engine, workflow, budget, actor, platform, runtime, daemon, CLI. Where registry validation resolves a not-yet-published development dependency, publish its already-verified archive with Cargo's verification skipped only after reviewing the package gate; resume normal verification once its cycle is available. Use an operator-controlled uploader that accepts the validated `.crate` bytes. Ordinary `cargo publish` may repackage the checkout (including VCS metadata and registry lockfile checksums); do not substitute that different archive under an existing manifest hash. Do not edit package manifests to bypass this cycle at publication time.
4. Publish GitHub release assets together: manifest, checksums, notes, API docs, all `.crate` files, `source.bundle`, conformance directory, profile/matrix, and every evidence file listed in the manifest. Exclude the diagnostic `scratch/` directory; its report/log subset is separately inventoried.
5. Record each registry and GitHub asset publication in the operator's release record with identity/hash and outcome. On partial failure resume only missing identical artifacts. Never retag, rebuild different artifacts under the same version, or declare completion while a crate or asset is missing.
6. Build/test the downstream example against the registry without overrides; record that post-publication evidence and downstream handoff. Actual downstream adapter certification is each downstream release's gate.

The source bundle contains the complete Git history needed for the selected commit.
To run conformance from downloaded assets:

```sh
git clone source.bundle actionqueue
cd actionqueue
git checkout --detach EXACT_MANIFEST_SOURCE_SHA
cargo run --locked --example aq_conformance --features workflow,budget,actor,platform -- --full --report "$TMPDIR/report.json"
```

A conformance-directory-only archive is insufficient: drivers import repository
harness code and boundary checks enumerate Git-tracked files. Checksums establish
integrity relative to the manifest, not publisher authenticity; distribute the
manifest through the operator-controlled release channel.
