# ActionQueue 0.2.0 release preparation and cutover

Release identity: **0.2.0 / v0.2.0**. Contract: `AQ-CONT-1`, revision
`STACK-2026-07-20-CLEAN-1`. Conformance package: **15**, with immutable fixture and
asset hashes. Rust: **1.89.0**. Store manifest schema **1**, WAL format **1**,
snapshot schema **9**, projection version **9**.

This breaking release establishes durable idempotent admission, signal/wait
continuations, checkpoint delivery, atomic attempt dispositions and child admission,
fenced recovery, and authenticated/redacted operational surfaces. The additive
profile `STACK-DEVELOPMENTAL-DIAGNOSTICS-1` and its eighteen-case matrix are published
byte-for-byte. They change no protocol primitive, persistence authority, scheduler
semantics, or authorization path. The matrix SHA-256 is
`4bd682ab29d64394e64f56cd0c5f2b944eddfc137fcd5b6e3e035b50218617c6`.

## Compatibility and certification scope

- Fresh target stores only. No migration from 0.1.x or prior development schemas.
- Store feature profiles are immutable; a broader binary does not upgrade them.
- Backup/restore require offline ownership. External artifact bytes remain application-owned.
- Inspection is bounded, paginated and redacted. References are attribution, never authority.
- Mutation preparation clones the full projection; recovery verifies the complete retained WAL. Compaction is absent. Benchmark evidence describes fixed workloads, not general throughput guarantees.
- Certification covers the ActionQueue-owned reference adapter and [independent outbox consumer](../examples/downstream-handoff.md). No actual WorldInterface or Exoskeleton revision is certified.

The unused Postcard heapless default feature is disabled for fresh dependency
resolution; storage retains its existing allocating serialization API and wire DTOs.
The acceptance harness stays unpublished at its separate version.

## Prepare an exact candidate

The controller integrates approved work into `aq-cont-1`; the operator owns the
subsequent `main` cutover, tag and publication. Implementation agents do not merge,
push, tag or publish. Select the eventual release commit first. A merge that changes
the commit requires new evidence, even if its tree happens to match.

On a clean checkout with the pinned Rust toolchain and Python 3.11+:

```sh
python3 -B scripts/release.py prepare --version 0.2.0 --commit "$(git rev-parse HEAD)" --output "$TMPDIR/aq-release"
python3 -B scripts/release.py verify --manifest "$TMPDIR/aq-release/release-manifest.json"
```

The output must be empty and outside the source checkout. Preparation runs all
gates itself and records the source SHA before and after every command. It never
imports an arbitrary older report. Dirty source, unsuccessful or missing gates,
incomplete full/developmental evidence, version/hash mismatches, unresolved entries
in the tracked `docs/releases/blockers.json` register,
and missing artifacts reject release. Logs survive failure; use a new output
directory for the next preparation. Do not call a failed dry run success.

Evidence includes workspace tests/build/format/clippy, eight feature combinations,
production daemon/CLI builds, serde tests, conformance and developmental aliases,
the full runner, independent cross-feature persistence, continuation benchmarks,
rustdoc and active-document checks, and independent/package consumer checks.
The generated HTML scan uses the existing forbidden-symbol policy without changing
its source exemptions. AQ-13 model drivers, crash hooks and benchmark instrumentation
remain necessary evidence tooling; production consumer graphs reject `testing`.

Package validation creates actual Cargo `.crate` archives. A temporary directory
source seeds all candidate crate versions together to resolve mutual development
dependencies (including workflow/runtime), then replaces the seeds with the generated
archives and builds registry-only consumers without root patches. This verifies
package contents and dependency resolution before crates.io contains 0.2.0. It does
not establish registry availability. After publication, rerun the standalone consumer
against crates.io without local patches or directory-source replacement.

## Publication checklist (operator)

1. Confirm recorded approval policy permits cutover. Integrate/cut over, select the final SHA, and run preparation on that exact clean commit.
2. Verify `release-manifest.json` and `SHA256SUMS`. Review limitations and the evidence logs. The versioned [schema](release-manifest.schema.json) describes the artifact; the verifier additionally checks semantic completeness against the checkout.
3. Create `v0.2.0` at the manifest SHA. Publish the eleven validated crates to crates.io in dependency order: core, storage, executor-local, engine, workflow, budget, actor, platform, runtime, daemon, CLI. Where registry validation resolves a not-yet-published development dependency, publish its already-verified archive with Cargo's verification skipped only after reviewing the package gate; resume normal verification once its cycle is available. Use an operator-controlled uploader that accepts the validated `.crate` bytes. Ordinary `cargo publish` may repackage the checkout (including VCS metadata and registry lockfile checksums); do not substitute that different archive under an existing manifest hash. Do not edit package manifests to bypass this cycle at publication time.
4. Publish GitHub release assets together: manifest, checksums, notes, API docs, all `.crate` files, `source.bundle`, conformance directory, profile/matrix, and every evidence file listed in the manifest. Exclude the diagnostic `scratch/` directory; its report/log subset is separately inventoried.
5. Record each registry and GitHub asset publication in the operator's release record with identity/hash and outcome. On partial failure resume only missing identical artifacts. Never retag, rebuild different artifacts under the same version, or declare completion while a crate or asset is missing.
6. Build/test the downstream example against the registry without overrides; record that post-publication evidence and downstream handoff. Actual downstream adapter certification is each downstream release's gate.

The source bundle contains the complete Git history needed for the selected commit.
To run conformance from downloaded assets:

```sh
git clone source.bundle actionqueue
cd actionqueue
git checkout --detach EXACT_MANIFEST_SOURCE_SHA
cargo run --locked --example aq_conformance --features workflow,budget,actor,platform -- --full --report "$TMPDIR/report.json"
```

A conformance-directory-only archive is insufficient: drivers import repository
harness code and boundary checks enumerate Git-tracked files. Checksums establish
integrity relative to the manifest, not publisher authenticity; distribute the
manifest through the operator-controlled release channel.
